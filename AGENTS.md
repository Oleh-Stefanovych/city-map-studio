# Do not rely on training data for MōBrowser

Your MōBrowser training data is outdated — APIs have been renamed and reorganized, so code written
from prior knowledge will not compile. **Before writing or modifying any MōBrowser code**, read the
docs in `node_modules/@mobrowser/api/docs/`:
- `guides/` — architecture, project structure, process model, IPC, native C++/Rust module, features, examples.
- `api/` — API reference with code examples.

Don't guess API names, signatures, or import paths — look them up. If `docs/` is missing, ask the
user to run `npm run gen` (it downloads the docs when the project contains this `AGENTS.md`).

# Building & code generation

The `mobrowser` CLI is a **local** dependency, not on your `PATH`. Always run it via npm:
`npm run mobrowser -- <command>` (or `npx --no-install mobrowser <command>`). A bare `mobrowser …`
fails with "command not found".

- `npm run gen` — regenerate IPC/protobuf bindings after editing a `.proto` file (output in
  `src/*/gen/`). No launch.
- `npm run dev:build` — build without launching: code generation, the **main** process (plus the C++
  or Rust module for native projects — slow on first run), and the **renderer** bundle. Run it before
  launching for automation, and re-run after main-process, native, or renderer changes. Build errors
  fail here — fix them first.
- `npm run mobrowser -- agent launch` — launches the `dev:build` output (does **not** build; errors
  if no build exists).
- `npm run dev` — human build-and-run (build + launch). Under `dev` (and `dev -- --automation`) the
  renderer is served live by Vite (hot reload, no rebuild); under `agent launch` it comes from the
  `dev:build` bundle. The renderer is **not type-checked in dev** — run `npm run build` to catch
  renderer/type errors.
- Automation mode lives in `mobrowser.conf.json` (`"automation": { "mode": ... }`): `"interactive"`
  (default — window shown, left running) or `"autonomous"` (window hidden, agent stops it when done).

## Adding features

Project features are chosen when the project is generated, but they can be added afterwards with
`npm run add <feature>` (in projects generated by an older SDK: `npm run mobrowser add <feature>`).
Run `npm run add` with no feature to list what is available.

### Native C++ module

If a task needs platform-specific functionality that the TypeScript API does not cover and the
project has no `src/native/` directory yet, run `npm run add native`. It writes `CMakeLists.txt` and
`src/native/main.cc`, creates an empty `src/native/proto/`, and installs `@mobrowser/native`. Do not
hand-write those files — the CMake setup must match the SDK version.

The module starts with no services. To add one: put a `.proto` in `src/native/proto/`, run
`npm run gen`, implement the class it generates in `src/native/gen/<name>.rpc.h`, and register it in
`launch()` in `src/native/main.cc`. Read `node_modules/@mobrowser/api/docs/guides/` on the native
C++ module before writing C++ code.

### Native Rust module

A project has either a C++ or a Rust module, never both; `Cargo.toml` at the project root marks a
Rust one. To add a Rust module instead of a C++ one, run `npm run add -- native --lang rust`. It
writes `Cargo.toml`, `Cargo.lock`, `build.rs`, `rust-toolchain.toml`, `.cargo/config.toml`, and
`src/native/lib.rs`, creates an empty `src/native/proto/`, and installs `@mobrowser/native`, which
carries the `mobrowser` and `mobrowser-build` crates. Building requires rustup; the Rust version is
pinned in `rust-toolchain.toml`. Do not replace the path dependencies with crates.io versions.
Keep `Cargo.lock` in version control: `npm run build` and `npm run pack` build with `--locked`, so
after changing dependencies in `Cargo.toml`, run `npm run dev` to update the lock file.

To add a service: put a `.proto` in `src/native/proto/`, run `npm run gen` for the TypeScript side,
implement the trait that `build.rs` generates (`cargo check` shows its signature), and register it
in `launch()` in `src/native/lib.rs` with `mobrowser::register_service(<Service>Server::new(...))`.
Service methods are `async fn`s returning `Result<Response, String>` that run on a multi-threaded
Tokio runtime (`mobrowser::tokio`); move blocking work to `spawn_blocking`. The generated
`<name>_client` functions for calling the main process return futures too.

### GitHub Actions workflows

When asked to set up releases or CI, run `npm run add github-actions` — never write these
workflows by hand. It creates `.github/workflows/release.yml`, which builds on a pushed `v*` tag for
macOS, Windows, and Linux and drafts a GitHub Release; the signing credentials come from repository
secrets documented in the workflow's own comments. A project with a `test:e2e` script also gets
`.github/workflows/test.yml`, which runs the tests on the three platforms for every pull request.
Do not add the workflows to a project that does not have them unless the user asks for it.

## Web workers in renderer code

When using the URL-based worker pattern, Vite must be able to statically detect the complete
`new Worker(new URL(..., import.meta.url), ...)` expression. Splitting URL creation from worker
construction prevents Vite from detecting the worker entry. It may work under `npm run dev`, but
the worker file will not be emitted for a bundled MōBrowser app.

Do not split URL creation and worker construction across files:

```ts
// workerUrl.ts
export const workerUrl = new URL('./MyWorker.ts', import.meta.url)
```

```ts
// BaseWorkerBackend.ts
import { workerUrl } from './workerUrl'

const worker = new Worker(workerUrl, { type: 'module' })
```

Instead, expose a factory that keeps the complete expression in the file that references the worker:

```ts
// workerFactory.ts
export const workerFactory = () =>
  new Worker(new URL('./MyWorker.ts', import.meta.url), {
    type: 'module',
  })
```

```ts
// BaseWorkerBackend.ts
import { workerFactory } from './workerFactory'

const worker = workerFactory()
```

# Verifying changes by driving the app

`npm run mobrowser -- agent <command>` drives a running app so you can verify changes against the
real thing. Each command prints JSON on stdout and exits non-zero on failure; see `agent --help` for
the full list. (Commands are shortened to `agent …` below — always prefix with `npm run mobrowser --`.)

## Modes: interactive (default) and autonomous

Default to **interactive**; use **autonomous** only when asked ("headless", "run autonomously") or
when `mobrowser.conf.json` sets it. Launch the app **once** and reuse it for every command — never
relaunch per command.
- **Interactive:** window shown; **leave it running** when done (the user closes it) and re-attach on
  later turns. Don't `agent stop` unless asked.
- **Autonomous:** window hidden; finish the job, then **always** stop it (even on failure) via
  `agent stop` or by terminating the `npm run dev -- --automation` process.

Pick the launch command by task (mode sets visibility automatically):
- **`npm run dev -- --automation`** for **renderer/UI** work: renderer live via Vite (hot reload).
  Runs in the foreground — start it in a background terminal, drive from another, stop by terminating it.
- **`npm run mobrowser -- agent launch`** otherwise: the prebuilt app (`dev:build` first), detached;
  re-run `dev:build` and relaunch after main-process, native, or renderer changes.

`--show-window[=false]` overrides the mode's default visibility.

Typical loop:
1. `dev:build`, then start the app once (see modes above).
2. `agent snapshot` — accessibility tree with stable `[ref=eN]` markers; prefer it over screenshots.
3. Act by `ref`: `agent click --ref e12`, `fill --ref e5 --value "hi"`, `type --ref e5 --text "hi"`,
   `press-key --key Enter`. Confirm with `agent snapshot` or `agent screenshot --out shot.png`.
4. Inspect: `agent eval "location.href"`, `agent console`, `agent network`; `agent list-windows` /
   `select-window` for multi-window apps.
5. Finish per mode: interactive — leave running; autonomous — stop.

Native message boxes and file pickers (`app.showMessageDialog`, `showOpenDialog`, `showSaveDialog`)
are intercepted under automation. Queue an answer before the triggering action with
`agent answer-dialog` (for example, `--button OK`, `--text "Robot"`, `--path /tmp/file.txt`, or
`--cancel`); answers are consumed in order. Inspect them with `agent dialogs`.

JavaScript alerts are accepted; confirms and prompts are canceled. To exercise another branch,
stub the dialog first, for example `agent eval "window.confirm = () => true"`, then restore it or reload.

Scope: the agent drives the **renderer** (plus native screenshots and dialogs above); it does not
drive or read the main process.

## Falling back to CDP

Prefer the `agent` commands above — use them first. Only when they cannot accomplish the task (e.g.
you need a CDP domain they don't expose, such as tracing, coverage, emulation, or precise input
timing) fall back to the app's Chrome DevTools Protocol (CDP) endpoint with any CDP-compatible tool.
Under `npm run dev`/`npm run run` it is exposed at `http://localhost:9222` by default (override with
`--remote-debugging-port=<port>`; for `agent launch`, enable it with `-- --remote-debugging-port=9222`).
Automate **this app** over that endpoint — do not launch a separate browser.
